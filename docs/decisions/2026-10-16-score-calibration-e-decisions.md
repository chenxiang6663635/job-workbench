## 背景（一句话）

E = **筛选校准**：把「先评分再投」的先验筛法与 tracker 里的后验结局接起来，
回答*「我按评分筛的这一套，测出来的结果支持它吗？」*。它**不**回答「该不该海投」，
**不**替用户放宽阈值（设计文档 §四 反目标）。

三个输出：① 按评分档位的转化率（分母=投过）② 未投递岗位的记账（只读）
③ 节点复盘的人话结论（一律「数据显示 + 可能」）。

---

## E-01 ｜ 分母 = 该档位里「投过」的岗位数

- **原始问题（逐字）**：「分母 = 该档位里「投过」的岗位数（§二 输出 ①）——这是本设计的
  关键口径，也是最容易做错的一处」（设计文档 §九.1）
- **当前实现（`8ceb999`）**：`web/backend/routers/dashboard.py:60` 的 `job_pool_overview`
  已有「档位 × 投递状态」**计数**，但**没有转化率**；转化口径的唯一实现在
  `report.py:243-257`（`conversion`）与 `report.py:227`（`retrospective`）。
- **备选项**：A 分母 = 投过数 ｜ B 分母 = 该档全部岗位数 ｜ C 两个分母都给
- **推荐：A**（C 由输出 ② 承载，不混进同一个分母）
- **理由**：本输出要回答「投出去之后成不成」；把没投的算进分母，等于把「我筛掉了它」
  混进「它转化好不好」——两个问题被搅成一个（设计文档 §二）。没投的那部分由输出 ②
  单独回答，口径更诚实。
- **影响面**：新领域模块 `score_calibration.py`（纯函数；不塞 `report.py` 535 行顶格、
  不塞 `tools_readonly.py` 登记水位）、`/api/dashboard` 加字段 + 看板一张卡、
  CLI 扩 `jobws report` 组 flag、MCP 新增只读工具 `score_calibration`、plugin 只加段落。
- **测试契约**：设计文档 §八.1——构造「同档位 1 投 + 2 未投」，断言分母是 **1**（不是 3）。
- **发行处理**：**本版实现**（v26.11.0 候选功能）。

## E-02 ｜ 档位沿用 `THRESHOLDS` 五档，样本不足 `shown=false`，不合并相邻档

- **原始问题（逐字）**：「档位沿用现有 `THRESHOLDS` 五档，逐档给、样本不足即
  `shown=false`（**不合并相邻档**凑样本）」（设计文档 §九.2）
- **当前实现（`8ceb999`）**：`jd_score.THRESHOLDS` + `verdict()` 是**唯一**档位实现；
  桶一已修 `verdict` 的闭区间缝隙（74.5 落档外 → 半开区间 + 显式失败），
  `tests/test_jd_score.py` 钉住边界。
- **备选项**：A 沿用五档 + `shown=false` ｜ B 合并相邻档凑样本 ｜ C 动态/自适应分档
- **推荐：A**
- **理由**：合并相邻档是用**结构手段**制造虚假样本量，直接违反反目标 3（不许拿小样本
  当趋势）；C 等于新造一套分档口径，违反「不新造分档口径」（§二）。样本下限照抄
  `report.cluster_failures` 的成熟范式（`MIN_CLUSTER_SAMPLES = 3` + `noteCode`），
  样本少时给百分比比不给更害人。
- **影响面**：同 E-01（档位判定复用，不新增口径）。
- **测试契约**：§八.2（未评分不入档但出现在 ② 的构成里）+ §八.3（投递数 < 3 时
  `shown=false` + `noteCode="too_few_samples"` 且**不输出百分比**）。
- **发行处理**：**本版实现**。

## E-03 ｜ 「放掉记账」写入口本批不做，只做只读的 ②

- **原始问题（逐字）**：「「放掉记账」的写入口本批不做，只做只读的 ②（规模与构成），
  写入口单独立项评估（因为它要动 schema 面与两段式写入）」（设计文档 §九.3）
- **当前实现（`8ceb999`）**：「放掉」这个动作**没有任何数据落点**（不生成 tracker 行、
  不改目录，事后无法回溯当时多少分、为什么放——设计文档 §五）。未投递枚举已有：
  `web/backend/routers/progress/job_dirs.py:121-128`（`apply_state == "未投递"`）。
- **备选项**：A 只读（规模 + 构成）｜ B 新增写入口（两段式 + schema + history 时间线）
  ｜ C 用目录时间戳/解析卡推断「当时为什么放」
- **推荐：A**，B 登记 ROADMAP 候选池（触发条件：用户真的要回溯「放掉」的理由）
- **理由**：B 要动 schema 面 + 两段式写入 + history 时间线，在发行冻结前属于扩大面，
  且应独立评审（`keep-writes-human-confirmed` 红线附近）；C 是**猜**不是数据
  （mtime 会被拷贝/同步污染），比不给更害人。
- **影响面**：只读统计；匹配键 = 目录名首个下划线切分，**公司名自带下划线会误判
  「未投递」**——输出必须带这条已知取舍说明（§八.6）。
- **测试契约**：§八.4（断言本特性**不产生任何写请求**：不写配置、不写 tracker、
  不调 `preview_*`——用请求监听/写口 mock 钉死）。
- **发行处理**：**本版只读**；写入口单独立项（候选池登记，不进 v26.11.0）。
