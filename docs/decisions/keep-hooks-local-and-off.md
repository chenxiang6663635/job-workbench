# 决策：宿主 hooks 保持本地、默认关闭，本批不实现

- 状态：已采纳（2026-09-22）
- 相关：`ROADMAP.md`（Now 里的 Skills & plugin distribution 一条）、`.githooks/`（已有的本地 git 钩子）、`docs/four-ends.md`（宿主专属字段登记）

## 背景

宿主（Claude Code 等）陆续开放了 hooks：在工具调用前后、会话起止等事件上执行外部命令。
它能固化「写完就查」这类流程，但代价与风险同样真实：

- **支持面窄**：目前只有 Claude Code / Cline / Kiro CLI 等少数宿主支持；其余宿主读到配置也只是忽略——同一份配置跨宿主不可移植。
- **它不是安全边界**：官方文档明确 `if` 过滤只是筛选、**不构成权限控制**；PreToolUse 超时不会阻塞、`exit 1` 也不阻塞（要阻断必须 `exit 2`）。把它当护栏用，得到的是虚假的安全感。
- **供应链面**：hooks 与技能一样可被分发，而「分发的配置里带一段自动执行命令」正是供应链事件最常见的形态（业界已有恶意技能基准与扫描工具）。
- **本仓库的定位**：本地优先、数据不出本机、写操作一律人工确认。任何「自动执行」都要先回答：谁来审计、怎么关、默认开不开。

## 决策

**本批不实现宿主 hooks**，并把边界写成显式约定：

1. 只保留**本地 git 钩子**（`.githooks/` 的 `pre-commit` / `commit-msg`），启用方式 `git config core.hooksPath .githooks`（见 `CONTRIBUTING.md`）——它们随仓库走、可读可审计、只影响本机提交。
2. 宿主 hooks **默认关闭**：仓库不分发任何宿主 hooks 配置（不写 `settings.json`，也不在插件壳里声明 hooks）。
3. 将来若引入，必须先满足四条：**默认关闭** + **显式启用**（写在用户自己的配置里）+ **只审计提示、不阻塞** + **不联网**；并在 `docs/four-ends.md` 的宿主专属字段表里登记。

## 已评估的替代方案

- **把检查塞进宿主 hooks**：收益是「写完即查」，但 CI 的七项门禁已覆盖同样的检查，本地 git 钩子也已能拦住提交——多一层自动执行换不来新的保障。
- **把 hooks 声明进插件壳**（`plugin.json`）：那样每个装插件的人都会继承这套自动执行，与「默认关闭」直接冲突。

## 复评条件

宿主 hooks 的支持面明显扩大（≥3 个我们支持的宿主），且出现「CI 与 git 钩子都覆盖不到」的具体场景时，再按上面的四条重启评估。
