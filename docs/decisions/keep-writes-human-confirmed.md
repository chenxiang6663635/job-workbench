# 决策：写入一律人工确认，不做自动投递与代登录

- 状态：已采纳（2026-09-22）
- 相关：`CONTRIBUTING.md`（写入两段式）、`docs/four-ends.md`（各端例外登记）、`skills/jwb-cli-contract`、`skills/jwb-api-review`

## 背景

求职工作台要碰的是「投递记录、简历、邮件、岗位池」这些**用户真实数据**，而且链条末端连着外部系统（招聘网站、邮箱）。任何自动化都必须先回答：写错了谁负责、能不能撤销、边界在哪。

几条现实约束：

- **招聘平台的规则**：批量/自动投递普遍违反平台条款，账号风险由用户承担；代登录意味着把用户凭据交给工具。
- **决策不可代做**：投不投、接不接 offer 是用户的价值判断，工具只能把事实摆清楚（分数、缺口、时间成本）。
- **错误会累积**：AI 抽取的每一条错误一旦自动写进数据，后续所有统计、提醒与材料都建立在错值上（Anthropic 在 agent 设计指南里专门警示过这一点）。
- **本地优先**：数据不出本机，写操作的审计面越窄越好。

## 决策

1. **写入一律两段式**：命令行 `--preview` → `jobws apply <令牌>`；AI 宿主 `preview_*` → `apply_approval`；界面弹窗确认（差异表）。没有直写口，也没有「跳过确认」的开关。
2. **三类事永不做**：不自动投递、不代登录、不替用户选 offer。工具只产出建议与材料，动作由用户按。
3. **AI 产出永不直接落盘**：解析、打分、改写一律先呈现（含原文依据与把握程度），用户逐条确认后才写。
4. **邮箱只读**：IMAP 只做只读拉取（`SELECT(readonly)` + `BODY.PEEK`），无后台轮询、无保活；状态改动只发生在用户确认后的两段式写回。
5. **可追溯**：写回的变更进时间线（谁改了什么、依据是哪句原文），删错可凭工作区外的整表快照恢复。

## 已评估的替代方案

- **全自动投递**：省几分钟，换来账号风险与大量误投，且用户回头要逐条清理——净收益为负。
- **AI 自动写回低风险字段**：「低风险」由谁定义？抽取错误的代价与字段无关（错的公司/错的阶段都会污染统计），确认一次的成本远低于修正一次。

## 复评条件

平台出现**官方**批量接口（带用户授权与回执），且用户明确要求时，可评估「半自动」形态——即便如此，第 1、2 条不变。
