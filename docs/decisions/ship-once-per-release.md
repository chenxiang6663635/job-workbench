# 决策：单一发布节点 + 时间戳版本号

- 状态：已采纳（2026-09-15 起执行；2026-09-22 留档）
- 相关：`CONTRIBUTING.md`（版本号体系与发布流程）、`ROADMAP.md`（Now 段的说明）、`tools/release_assist.py`、`.github/workflows/release.yml`

## 背景

本项目的使用者主要是作者本人（自用优先），发布的意义是「一个可以回头的稳定点」，不是「持续交付」。此前按批次连续发版带来了两个真实代价：

- **升级成本落在用户身上**：每次安装都要重来一遍（真机冒烟、旧数据打开、桌面壳），而多数批次之间并没有必须立刻拿到的能力。
- **版本号没有语义**：`0.x.y` 这类数字在自用工具里既不表达兼容性，也不表达时间，翻 changelog 才知道哪个版本有什么。

对照业界做法：CalVer（`calver.org`）主张用日期表达时间；PEP 101 的发布演练（`git push --dry-run --tags`）说明「发布本身要有预案」；release train（单一发布节点）适合**协调型**发布——多件事攒到一个节点、一次验收。

## 决策

1. **版本号用时间戳**：发布号 `YY.MM.DD.N`（当日第 N 次发布），机器可读版本（`package.json` / `latest.yml` / 产物文件名）是当日 `YY.M.D`，tag 为 `v<发布号>`。校验在 `tools/release_assist.py`（`jobws release check`），只比日期三段、`N` 不参与。
   > **2026-09-24 更新（本条已被取代）**：改为**月粒度 CalVer `YY.MM.N`** 单一形态（`26.9.0` 首发、`26.9.1` hotfix、换月清零；tag 与 CHANGELOG 段名同号）。原因：electron-updater 的版本比较走 Node semver，四段与补零月份都非法——自动更新会在首次发版时失效。其余内容（单一发布节点）不变。
2. **单一发布节点**：所有批次先在 `main` 落地（各自一个 PR、各自 CI 绿），**中间不 tag、不 Release、不出包**；攒到发布日一次性发，并整体归入当日的版本段。
3. **发布可演练**：`release.yml` 支持 `workflow_dispatch` + `dry_run=true`，先跑一遍完整构建与资产核验，再决定是否真发。
4. **已知取舍写在这里**：`YY` 有世纪歧义（CalVer 官方建议 `YYYY`）——本项目的号只用于自用工具的更新比较，保留 `YY`；CalVer **不表达破坏性变更**，所以破坏性变更必须在 CHANGELOG 显式列出（见 Keep a Changelog 的过渡约定）。**2026-09-24 起「四段」取舍已作废**——改为月粒度 `YY.MM.N` 三段（见上方更新注记），「同日重发」的诉求由第三位 N 承载。

## 已评估的替代方案

- **每批一发**：升级成本 × 批次数，收益是「更早拿到能力」——对自用工具不成立。
- **semantic-release / release-please 自动发**：与单一发布节点冲突（它们默认每次合并即发），且要引入 Node 工具链与仓库写权限。
- **只打 tag 不出包**：桌面壳的用户拿不到升级，等于没发。

## 复评条件

出现**第二个真实使用者**且需要更快拿到修复时，可评估「热修通道」（在两次正式发布之间只发修复，即当月的 N 递增版本），但单一发布节点的验收纪律不变。

**2026-09-25 收口批补充**：以下四类问题**不等待上述复评条件**，可直接走 `26.9.N` hotfix——**安全漏洞**（含凭据泄漏路径）、**数据损坏 / 静默覆盖**、**安装 / 启动阻断**、**更新链失效**。理由：这四类的暴露时间由"下一次正式发布"决定，而正式发布节点可能还有数周的功能批次在排队——把它们绑在功能节奏上，等于用用户的安全性为发布纪律付账。hotfix 仍须过完整门禁与 dry_run（验收纪律不变）。
