### 二之二、tag 树实测记录（2026-10-16，探针法）

**方法**：`git switch --detach v26.10.0` → 用 `git show main:tests/...` 把 `main` 的
`test_dual_root_same_workspace.py`（12 条）与 `test_cli_data_root_persisted.py`（2 条）
原样写入 tag 工作树（未跟踪）→ 跑 → 删探针、回 `main`。**契约网不动一字**，红绿即
"v26.10.0 是否满足现行契约"的判据。

| 探针 | tag 上结果 | 说明 |
|---|---|---|
| 双根契约网（12 条） | **6 红 / 6 绿** | 5 条原缺陷全复现 + 多红 1 条 |
| CLI persisted（2 条） | **2 红** | ① `default_workspace()` 落应用根（真缺陷）② `tracker.resolve_workspace_arg` 在 tag 上**不存在**（API 缺失，非行为缺陷） |

**多红的那一条（新发现，原矩阵未列）**：`JOBWS_DATA_DIR` 指向**不存在**的根时，
`GET /api/applications?ws=personal` 返回 **200 + 应用根的 A_ONLY 数据**——即显式 env
失效时也静默回退应用根，且**没有任何闸拦着**。

**实测出的机制差异（独立探针，非推断）**：同为「显式根不存在」，两条路径行为不同——

| 场景 | tag 上 `data_root()` | `allowed_roots()` | `GET ?ws=personal` |
|---|---|---|---|
| `env` = 不存在的根 | 该（不存在的）路径 | `[应用根, 该路径]` | **200 + A_ONLY**（静默回退，无闸） |
| `persisted` = 不存在的根 | 该（不存在的）路径（`readable=True`） | `[应用根, 该路径]` | **503**（可用性闸 fail-closed） |

即：**persisted 路径有可用性闸兜底，env 路径没有**。这与 `main` 上 #312 补证后的
"两种都 fail-closed"相比，是 v26.10.0 的一处真实差距（env 场景暴露面更大）。

## 三、触发条件与暴露面（hotfix 裁决的依据）

1. **P2**：需「应用根与数据根**同名工作区**」+ 带 `ws` 的请求。
   - NSIS 安装形态（Program Files，只读）：**推断**写路径会响亮失败（OS 只读 → 原子写抛错 → 500）而非静默污染——**未实测**，隔离环境安装后验证列为 G2 动作；读路径可能返回安装目录里的旧副本（若用户曾在安装目录留下同名工作区）。
   - 便携 / 源码形态（应用根可写）：读旧数据 + **写落旧副本**（真实污染）。
   - 默认安装流程不在应用根建工作区（新建落数据根）→ 触发需**非默认布局**；至今无实际报告。
2. **#313**：需「用户在设置页记住过数据根 B」+「A/B 都有 `personal`」+ 用 CLI 且不带 `--workspace`。写暴露同样只在应用根可写时成立（源码/便携）。
3. **P1-B**：需用户主动走 data-root 迁移的「搬回旧位置」路径，并看到误导性「已是当前数据」文案（#305 已改为如实说明"反向迁移当前不可行"）。
4. **S2**：需工作区内已有指向外部的 symlink/junction（用户不可感知的材料）+ 读取经模型代传路径参数。可利用性维持此前"低"的判定，且 **v26.10.0 并未缺失核心防护**。

## 四、可立即给用户的规避措施

- 核对两处是否存在同名工作区：安装目录（或仓库根）与数据根（设置页「数据位置」会显示当前根与来源）；
- CLI 显式传 `--workspace <数据根>/personal`，或设 `JOBWS_DATA_DIR=<数据根>`；
- 不执行「搬回旧位置」的迁移，等 26.11.0。

**裁决**：第二档证据下的**暂定**裁决；第三档证据取得后转为正式裁决（见下方签署条件）。

**理由**：四条风险的共同触发前提都是**非默认布局**（双根同名 / 记住过数据根 / 主动
迁移 / 已有外部链接），无已知实际事故；NSIS 安装形态（绝大多数用户）下写路径因只读
而失败，不构成静默数据分叉；hotfix 需要一条完整第二发布链（从 tag 挑 5+ 修复、重建、
重签、重发），代价与风险高于收益；`main` 已含全部修复，发布链会做真机 + 回滚验证。
本轮新实测的两点**不改变**上述理由，但**扩大了对 env 场景的暴露面认定**：
① `JOBWS_DATA_DIR` 指向不存在的根时旧版静默回退应用根（200 + 旧数据）；
② 同场景下 persisted 有 503 闸、env 没有——两条路径不一致本身也是缺陷形态。

**升级为 hotfix 的条件（任一命中即重启评估）**：
- 出现任何真实报告（数据"消失" / 被覆盖 / 两端不一致）；
- G2/G3 隔离环境实测证明 NSIS 安装形态下也存在**静默**错根写（而非 500）；
- 用户要求提前修。

**留待发布链（G2/G3，须用户在场）——本裁决转为正式的必要条件**：
1. 隔离环境安装 v26.10.0（本机两次尝试均被 UAC 交互阻断，故须用户在场执行）；
2. 对 **P2 错根写**与 **S2 越界**各做一次定向探针，用临时目录、不碰真实数据；
3. 对 §二之二 新发现的 **env→不存在根** 场景补一次探针（安装形态下是否同样 200 回退）；
4. 结果回填本节，裁决由"暂定"改"正式"。

## 六、S4 落地当天发现的两个门禁自身问题（同日修正）

**(1) 规则集与 workflow 触发条件耦合 → 纯文档 PR 永久 BLOCKED（已修）**

本 PR（#317，纯文档）合并时 `mergeStateStatus=BLOCKED`，而全部检查均 pass。根因：
`codeql.yml` 的 `pull_request` 带 `paths-ignore: ["**/*.md", "docs/**"]`（本意是省
CI），于是纯文档 PR **完全不触发 CodeQL**；而 S4 新建的 ruleset
`codeql-merge-protection`（`code_scanning` 规则）要求每次 PR 都有 code scanning
结果——没有结果可验 → 永远 BLOCKED。这正是审计预警的「工作流未触发使所需检查无法
满足」陷阱（#316 当时能过，只因它同时改了 `ci.yml`、不在 ignore 列表里，属侥幸）。

**修正**：`codeql.yml` 的 `push` / `pull_request` 去掉 `paths-ignore`——每个 PR 都
产出 code scanning 结果，ruleset 才可满足。代价是文档 PR 也多跑一两分钟，正确性优先。
教训：**给门禁加规则集/必需检查时，必须同时核对该检查的产生条件（paths/if/concurrency）**，
否则会把"跳过"变成"永久卡住"。

**(2) UI 冒烟抖动（重放即过，已按抖动处置）**

本 PR 首次运行 `UI 冒烟（布局 + a11y）` **失败**：axe `color-contrast 3.95`
（前景 `#8c96ac` / 背景 `#26375e`）命中 IMAP 拉取对话框内一个按钮，快照显示对话框
处于 `data-state="open"`（开场动画中）。同一提交重跑 → **pass**；此前 #314/#316 同样
代码均 pass。判定：**重放期抖动**（动画中 computed style 导致对比度测算偏差），非回归。

处置约定（S4 之后该检查是 Required，抖动的必需检查会误锁 PR）：
1. 失败先看"同一提交重跑是否即过"——是则按抖动处理，重跑后合并，并在 PR 留一句；
2. 同一提交连续两次失败 → 按真回归处理，不许靠重放掩盖；
3. 同类抖动反复出现（≥3 次/周）→ 单开 issue 收 e2e 稳定性（等对话框动画结束再扫），
   **不改检查口径**。
