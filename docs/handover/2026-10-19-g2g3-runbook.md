
> 2. **给隔离 home 补凭据**。**注意（2026-10-20 实测，与初稿不同）**：
>    - **复制 `~/.dsh/.credentials.yaml` 进隔离 home 不够**——该文件里凭据存放在
>      `records.*`（OS 凭据库引用/设备令牌）与 `refs.*` 下，headless 起不来时内置
>      `headless` profile 会**快速报错**：`MISSING_CREDENTIAL: llm-deepseek: no API key
>      for provider route "deepseek-official"`；
>    - **可行做法**：从该文件的 `refs.DEEPSEEK_API_KEY` 取值，**注入子进程环境变量
>      `DEEPSEEK_API_KEY`**（不打印、不落盘）；
>    - **profile 必须用内置 `headless`**：用 `dsh plugin --profile <自建名> add` 造的
>      自定义 profile 在缺凭据时会**静默挂起**（零输出、`--json` 也不出事件），而内置
>      `headless` 会给出明确的 MISSING_CREDENTIAL 报错。装法：把两个 tarball
>      `dsh plugin --profile headless add <子包> <主包>` 装进去即可（仍用隔离 DSH_HOME）。
>    - **代价**：会用你的额度，且虚构 DEMO 数据会被发给模型服务商（内容是假的，可接受；
>      但别在同一个环境跑真实数据）。**测完删掉隔离 home 里的凭据副本**。

> 5a 首轮 **300s** 未完成并经**同会话续跑**（`5a-final`）才拿到最终答复——有凭据 ≠ 不会超时，
> 超时 ≠ 插件失败。后续单场景**初始预算 600s**（执行预算，不是性能达标阈值）；超时只记
> `TIMEOUT/INCOMPLETE`，**不得**按失败或成功直接归类。续跑必须保留原会话标识、实际工具调用、
> 最终答复与磁盘差异；**不得自动重新执行可能产生写入的步骤**（5a 与 5a-final 不是两次独立样本，
> 不得当作两个成功证据）。连续超时或卡在同一工具时，记录原因并单独调查，不靠不断提高上限
> "修复"。只有完整最终答复与产物状态核验完成后，才判 PASS/FAIL。

## 七、结果如何改变裁决

> **两个裁决必须分开（2026-10-19 审计纠正）**：新版通过**不能**证明旧版无需 hotfix——
> 它们验的是不同制品、回答不同问题。

### 裁决一 · 旧版风险 → `26.10.1` 发不发（只看 **A 组**：已发布的 `v26.10.0`）

只根据 A 组实测回答三件事：错根写在旧版是否**实际可达**、是否可能改到另一份**真实台账**、
能否可靠识别与恢复。三项探针在**新版**上全过，**不构成**旧版无需 hotfix 的证据。
结论二选一：**发**（附旧版实测证据）/ **不发**（附"旧版不可达或风险可接受"的证据）。

### 裁决二 · 新版能不能落章（只看 **B 组**：从候选 `6b52a88` 构建的制品）

> **顺序修正（2026-10-20 审计）**：原稿写「C 组全部符合 → 进 G4 落章」是**循环**——
> C 组是「十一月落章后重建的最终制品」（§三），它不可能在 G4 之前被验证。
> 正确顺序：**B 组候选制品验收合格 → G4 版本落章与最终重建 → C 组最终制品回归验证
> （与 B 同判据重跑）→ G5 正式发布**。

- B 组三项探针 + §六 五项全部符合判据 → **具备落章条件**；
- 任一项不符 → 按 G1 纪律只接该阻断修复，修完重跑 §二 再落章；
- **§六 第 5 项「不假装完成」不符 → 即使桌面端四项全过也不落章**（npm 独立安装是本版
  新增形态，用户最先接触的就是它）。

B 组（候选制品）证明「构建产物与候选源码一致」+「新版是否已修」；它是 **G4 落章的前置**，
但不是 G5 的前置——G5 的前置是 C 组回归通过。C 组（落章后重建）只做**回归验证**：
与 B 组同判据重跑一遍；不过 → 按阻断修复流程处理，修完重跑 §二 与 G4，**不得带病进 G5**。

## 八、虚构数据隔离检查结果（2026-10-20 实测，8/8 通过）

在动手跑真机之前，先把"夹具会不会污染真实数据"这件事**用数据说清**。全程无 GUI、
不启动 DSH、不碰用户数据（只读哈希）。

| # | 检查项 | 结果 |
|---|---|---|
| 1 | 夹具 A 根（`A_ONLY`）建成 | PASS 17 个文件 |
| 2 | 夹具 B 根（`B_ONLY`）建成 | PASS 17 个文件 |
| 3 | 夹具 A 内容只含 `A_ONLY` | PASS 不含 `B_ONLY` |
| 4 | 夹具 B 内容只含 `B_ONLY` | PASS 不含 `A_ONLY` |
| 5 | 默认根空（覆盖 `APPDATA`、**不设** `JOBWS_DATA_DIR`）→ 自动初始化 | PASS 工作区已建，**14 个文件** |
| 6 | 自动初始化后注册工具数 | PASS **17 个**（真实 MCP 握手计数） |
| 7 | 显式 `JOBWS_DATA_DIR` 指向不存在的根 → 拒启 | PASS exit 2，**该目录未被创建** |
| 8 | 真实数据根哈希前后一致 | PASS `44f39b460bc13953` → `44f39b460bc13953` |

### 关键路径澄清（执行人务必知道"真实数据"是哪个）

数据根解析优先级是 `JOBWS_DATA_DIR` > 持久化选择 > **legacy** > 新默认；
**B3 起新默认 = `<user_data_dir>/data`**，而旧位置若已有真实工作区则**原样保留**（不搬迁）。

所以本机同时存在两种形状，**都不是 bug**：

| 形状 | 路径 | 何时出现 |
|---|---|---|
| **legacy（真实数据在这）** | `%APPDATA%\job-workbench\personal` | 桌面端历史工作区；**MCP-only 形态会优先选它** |
| 新默认（隔离环境会建在这） | `%APPDATA%\job-workbench\data\personal` | 全新环境（无 legacy、无持久化选择） |

实测确认：本机 MCP-only 形态解析到 `C:\Users\cx\AppData\Roaming\job-workbench`
（source = `legacy_userdata`），默认工作区 `...\job-workbench\personal` **存在**——
即 **DSH 插件能看到桌面端的数据，不是两套数据**。

> 因此：跑隔离测试时若要"新默认"形状，就**覆盖 `APPDATA` 到临时目录**；
> 若要"legacy"形状，就**覆盖 `APPDATA` 且在同目录下预置 `job-workbench\personal`**。
> 直接设 `JOBWS_DATA_DIR` 指向不存在的路径永远是 fail-closed（判据见 §六 DSH 1b）。

### 两个环境限制（会让人误判成产品缺陷）

- **frozen exe 在 `%TEMP%` 下建目录会 `WinError 5`（拒绝访问）**，同一条命令在仓库目录下
  正常——这是本机沙箱对 TEMP 的限制，**不是代码问题**。所以隔离的 `APPDATA` 要放在
  仓库内（`.codebuddy/tmp/...`），不要放 `%TEMP%`。
- **`JOBWS_DATA_DIR` 指的是数据根（`personal` 的父目录）**，不是工作区本身。传错会导致
  "工作区不存在"。

### 仍需真人操作的最小步骤（自动化覆盖不到的部分）

1. **UAC 与安装/卸载/升级/回滚**（§三）：要人点确认框、看托盘、确认数据目录保留。
2. **DSH 会话内两类 PDF 冒烟**（§六 第 5 项）：要人在宿主里提问并观察答复；随后核对磁盘
   是否真的出现 PDF（模型说"已生成"而磁盘上没有，正是要抓的编造）。
3. **应用健康确认**：主界面能进、会话正常、插件列表无异常变化。
4. **两处裁决签字**：旧版 `26.10.1` 发不发（看 A 组）、新版 `26.11.0` 能不能落章（看 C 组）。

> 以上四步之外的（干净构建、17 工具握手、fail-closed、夹具准备、越界探针）都可以自动化。
