## 一、四层身份：哪层证明了，哪层没有

审计用一张表把「连到哪个实例」拆成四层。这是本文档的组织骨架。

| 层 | 需要证明什么 | 现在谁负责 | 状态 |
|---|---|---|---|
| 健康状态 | HTTP 能响应 | `status` 字段 | ✅ 一直有 |
| **产品身份** | 是 Job Workbench，不是别的服务 | `service: "jobws"` | ✅ **已修** |
| **实例身份** | 是本次启动/被授权的那个实例 | `instance_id` | ✅ **已修**（启动路径） |
| **数据身份** | 指向预期数据根 | 无显式校验 | ⚠️ **部分**：自有子进程排除了「误连别人」，但数据根本身仍由统一解析器决定 |

> **不要把最后一行读成「已保证」**（2026-10-28 审计指出）。`backendEnv()` 是 `{ ...env, ... }`——
> 它继承父进程环境，**没有显式固定 `JOBWS_DATA_DIR`**。所以准确的说法是：
>
> > 自有子进程 + 实例身份校验，防住了「连到另一个 Backend」；但**解析出来的数据根**
> > 仍由统一解析器按「环境变量 → 持久化选择 → 默认规则」决定。
>
> 这是两项不同的性质。前者已修，后者**没有专门验收**。

### 为什么数据身份没有显式校验

ADR `port-identity` 规定：复用的后端用**它自己的**数据根。把数据根做成拒绝条件会让
「dev 后端 + 桌面壳」的复用直接失效。

而**默认不复用**这条改动，恰好把数据根风险的主要面消掉了：

| 路径 | 数据根会不会不一致 |
|---|---|
| 启动自己的子进程（默认） | **排除了「连到别人」，但不等于「根一定对」**——子进程是我们 spawn 的，可数据根仍由解析器决定 |
| `JOBWS_ALLOW_REUSE=1` 的复用 | **会**——用被复用实例自己的根，那是用户显式选择的 |

## 二、P0-A：实例身份

**原来的问题**：`/api/health` 只回 `{"status":"ok"}`，前端只查 `status`。
`{"status":"ok","service":"unrelated"}` 会被当成本工作台的后端。

**修法（四层）**：

| 位置 | 改了什么 |
|---|---|
| `web/backend/main.py:166,171` | `/api/health` 返回 `service` / `version` / `instance_id` |
| `web/backend/identity.py:29`（`is_our_service`） | 判据加 `service == "jobws"`（从 main.py 抽出，见 §五） |
| `web/electron/backend_identity.js:36`（`isHealthy`） | `status` + `service` + 可选 `instance_id` |
| `web/electron/backend_identity.js:24`（`INSTANCE_ID`） | 每个 Electron 进程随机生成一次 |
| `web/electron/backend_process.js:54` | 经 `backendEnv()` 注入子进程 |
| `web/electron/main.js:117`（`decideStartupAction`） | 三态决策，**默认不复用** |

**关键设计**：`instance_id` **不是鉴权**。本地 API 的 token / Origin / Host 保护是
另一项安全合同，没做。

**证据**：

| 测试 | 覆盖 |
|---|---|
| `web/electron/backend_identity.test.js`（7 项） | 产品身份 / 实例身份 / 四类拒绝 / 三态决策 |
| `tests/test_health_identity.py`（5 项） | `service` 存在 / `version` 真实 / **`instance_id` 回显** / 空串语义 / 不泄漏数据根 |
| `tests/test_port_identity.py`（5 项） | `_is_our_service` 的判据 + 缺字段拒绝 |

**残余风险**：`isHealthy` 的 `reason` 分布此前没有断言——现补到「6 个 reason 里 5 个
有字符串断言」，`timeout` 分支仍无断言，见 §七 第 1 条。

## 三、P0-B：进程保护

**原来的问题**：`start.ps1` 发现 8765 / 5173 被占用就 `Stop-Process -Force`，
而且 `-CheckOnly`（声称只检查环境）会先走到那段。

**修法**：

| 变更 | 位置 |
|---|---|
| 删除强杀（全文件 `Stop-Process` = 0） | `web/start.ps1` |
| 端口检查挪到 `-CheckOnly` 返回点**之后** | 返回点 L147 → 检查 L164 |
| 端口被占：打印 PID + 处置建议 + `exit 1` | `web/start.ps1:160-174` |

**证据（静态）**：

```
实际 Stop-Process 调用：无 ✓
-CheckOnly 返回点 L147 < 端口检查 L164 ✓
-CheckOnly 之前无文件写 / 建目录 / 装依赖 ✓
```

**证据（动态）**：⚠️ **未做**。「-CheckOnly 零副作用」目前是**控制流推断**，
没有在端口被占时实跑一次并比对进程列表。

**用户文档已同步**：`docs/usage-guide.zh-CN.md` 与 `docs/usage-guide.md` 里
「会自动清端口」+ 强杀命令已删（那会让用户复现 2026-09-25 的误杀事故）。

## 四、P0-C：Electron 安全公告

**问题**：`v26.10.1` 与 `main` 都锁 `electron 44.4.5`，受影响范围 `44.0.0-alpha.1 ~ <44.9.1`。

**已修**：升级到 **44.10.0**（#439）。声明改为 `^44.9.1`（公告的最低修复版）。

**证据**：`web/electron/package-lock.json` 的 `node_modules/electron.version = 44.10.0`；
`dist/` 73 文件 / 367 MB；`check_packaging` OK。

**残余风险（必须知道）**：

1. **已发布的 `v26.10.1` 仍是 44.4.5**——用户手里的版本不受本轮修复影响。
   要不要出 `26.10.2` 是独立决策（见 `2026-10-28-electron-tls-advisory-review.md`）。
2. **本机装 Electron 二进制必须走镜像**：`npm install` 只装 JS 包，
   `dist/` 要手动 `install.js` + `ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/`。

## 十、测试路径隔离与历史影响评估（2026-10-28）

> 起因：`tests/test_snapshot_restore.py` 的快照目录曾经**问应用要**而不是问临时目录要，
> 于是「测试全绿」与「测试没碰真实用户数据」在这里是两个不同的性质。修复见 #451。

### 事实（修前 vs 修后）

| 项 | 修前 | 修后 |
|---|---|---|
| 快照根来源 | `pathres.snapshot_root()`（Windows 读进程级 `APPDATA`，**调用时**读、无缓存） | autouse 夹具把它钉在 `tmp_path/snapshots` |
| 受影响的用例 | **1 条**：`test_retention_keeps_one_per_window_and_removes_the_rest` 不取 `client`，拿不到隔离 env | 0 条（与是否带 `client` 无关） |
| 破坏性动作 | 该用例写三个空 zip 后调 `_apply_retention`，它会列该目录**全部** `.zip` 并按策略删掉不入选的 | 只作用于 `tmp_path` |
| 守卫 | 无 | `_snap_dir` 断言快照根落在 `tmp_path` 下（`is_relative_to`），夹具失效即红 |

其余 29 条用例带 `client`，夹具的 `APPDATA` / `XDG_DATA_HOME` 一直有效——不是「一半用例都中招」。

### 结论与边界

- **写入发生过、删除行为存在**（源码与 mtime 均可证）；
- **没有任何证据表明用户的真实快照丢失**：只有「真实工作区恰好叫 `ws-ok`」才会被波及，
  而这一点无法从仓库回溯证明——`personal/` 的两份真实快照完整；
- 四个其他目录**归因不明**，不得按目录名当作残留清理；`personal/` 尤其不是残留；
- 不要为了复现再跑旧版测试（会再次修改真实目录）。审计侧已经意外改过一次 `a.zip` 的 mtime。

### 仍未做的（别把本节读成「测试全都不碰真实数据了」）

- 其余破坏性路径**尚未逐个盘点**：删除留痕（`*-deletes`）、数据根迁移、批量导入、清理操作；
  它们目前靠各自的 `monkeypatch.setattr(pathres, "snapshot_root", ...)` 或 env 隔离，
  但没有像本文件这样的**包含性断言**做兜底；
- Ubuntu CI 覆盖了 `is_relative_to` 守卫的普通路径（`pytest tests/` 在 ubuntu-24.04 上跑，
  该文件无 skip 标记）；**macOS 与「`/tmp` 是符号链接」的构造场景没有验证**。
