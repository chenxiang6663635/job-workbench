## 三、DSH 构建：**重编译运行时 ≠ 生成清单**

这两步经常被混为一谈，但顺序和职责都不同：

| 步骤 | 命令 | 做什么 |
|---|---|---|
| ① **重建运行时** | `pwsh -File scripts/build_mcp_exe.ps1 -FromLock -BasePython "<基础解释器>"` | 按依赖锁**重新编译** `jobws-mcp.exe` 与 `_internal/` |
| ② **生成清单** | `python scripts/mcp_prebuilds.py` | 扫描 `bin/` 现有文件，重算 227 条 SHA256，写 `prebuilds.json` |
| ③ **校验清单** | `node scripts/verify_mcp_prebuilds.js integrations/dsh/platform/win32-x64` | 逐条比对哈希 |
| ④ **17 工具冒烟** | 见 `docs/handover/2026-10-28-dsh-first-release-runbook.md` | 确认 MCP 服务能起来并列出工具 |

**为什么不能跳过 ①**：

```
只改 package.json 的 version → 跑 ② → 跑 ③ → 全绿
但 bin/ 里仍是旧构建 → 「清单合法，运行时是旧的」
```

`mcp_prebuilds.py` 只做哈希扫描，**不编译**。上一版文档把这件事写成
「`python scripts/mcp_prebuilds.py` = 重建」，那是错的。

**顺序也不能反**：② 读的是 `integrations/dsh/package.json` 的 `version`，
所以先改 ⑥ 再跑 ②，否则清单会写进旧版本号。

### 3.1 待动态验证：`SOURCE_DATE_EPOCH` × 清单提交顺序（2026-10-31 审计 §5）

`build_mcp_exe.ps1:65-73` 把 `SOURCE_DATE_EPOCH` 设为**本 commit 的时间**（不设则两次构建
的 wheel sha256 就不同，实测 `062669d1` vs `937c80d8`），而 `prebuilds.json` 是要**提交**
的生成物。于是存在一个未被验证的组合：

```
提交 A：改版本号 → 在 A 上构建 → 得到 bin/ + 清单
提交 B：把清单提交入库（HEAD 变了 → SOURCE_DATE_EPOCH 也变了）
在 B 上重新构建 → 是否仍得到与已提交清单一致的字节？
```

**已证明的**只是「同一 commit、同一构建条件下两次构建逐字节一致（227/227）」；
它**不能**推出「提交清单后再从新提交重建仍一致」。

**判据（写进验收收据）**：在**最终冻结提交**上重建的 DSH 运行时，必须与声明的制品身份
一致；若不一致，先查 `SOURCE_DATE_EPOCH` 与「构建 → 提交清单」的先后关系，
**不得**把带未提交变化的构建收据标成干净状态，也不得只重生成清单来掩盖差异。

## 四、动态验收：数据根（30 分钟）

### 4.0 先说清两件容易出错的事

**① 没有 `jobws dashboard` 这个命令。**

`tools/jobws.py` 的合法顶层命令是 `track` / `report` / `resume` / `prefs` /
`doctor` / `data-root` 等，**`dashboard` 是 Web 界面的页面，不是 CLI 命令**。
上一版文档写了 `jobws --workspace personal dashboard`——它必然失败。

**② `instance_id` 在手动启动时是空串，不能当实例证明。**

`main.py` 的 `health()` 里：

```python
"instance_id": os.environ.get("JOBWS_INSTANCE_ID", ""),
```

注释写明「空串表示『不是受控实例』（手工 `uvicorn main:app` 起的、或旧版壳）」。
所以用 `python main.py` 手工起 A 时，`/api/health` 的 `instance_id` **是空的**——
它只能证明「这不是 Electron 拉起的那个」，**证明不了「A 和 B 是两个不同实例」**。

要区分实例，得看**进程 PID**（`Get-NetTCPConnection -LocalPort 8765 | select OwningProcess`），
不是看这个字段。

**②b `/api/health` 不回数据根——这是设计，不是缺陷。**

`health()` 的 docstring 原话：

> 刻意不返回数据根：ADR port-identity 规定复用的后端用它自己的数据根。

回读数据根要用 **`GET /api/system/paths?ws=<name>`**，取 `dataRoot` 字段
（`web/backend/routers/system.py:189`）。

**③ 默认拒绝复用返回 `1`，不是 `2`。**

`web/backend/main.py` 的四条退出路径：

| 行 | 退出码 | 场景 |
|---|---|---|
| `:266` | **2** | `--host` 非环回且没加 `--unsafe-network-api` |
| `:287` | **0** | `JOBWS_ALLOW_REUSE=1` 时复用并打开界面 |
| `:298` | **1** | **默认拒绝复用**（端口上有本工作台后端） |
| `:302` | **1** | 端口被其他程序占用 |

>`2` 是 `--host` 那条的码，与端口冲突无关。

**这条错误的危险性**：`jobws` 的**用法错误也返回 2**。如果拿
`jobws ... dashboard`（不存在的命令）当测试，它会返回 2，而文档里写的期望
正好是 2——**假阳性就这么产生了**：测出来「通过」，实际什么都没验。

### 场景 1：默认模式（后端入口）

**在哪跑**：`web/backend/`

```powershell
# A：占住 8765
cd web/backend
$env:JOBWS_DATA_DIR = "<根 X>"
python main.py --port 8765

# B：另开一个终端，不设 JOBWS_ALLOW_REUSE
cd web/backend
python main.py --port 8765
```

**判据**：

| 观察点 | 期望 | 为什么 |
|---|---|---|
| B 的退出码 | **1** | `main.py:298` |
| stderr 文案 | 说清「已有一个本工作台的后端在运行」+ 三条出路（用它 / 设 `JOBWS_ALLOW_REUSE=1` / 换端口） | `main.py:289-296` |
| A 是否被杀 | **否** | 这是历史事故点，必须显式看一眼 |
| B 是否打开浏览器 | **否** | 拒绝路径不调 `webbrowser.open` |

### 场景 1b：默认模式（Electron 入口）

**在哪跑**：`web/electron/`

```powershell
cd web/electron
npm start
```

**判据**：

| 观察点 | 期望 |
|---|---|
| 弹窗内容 | 说清端口被**另一个实例**占用，并给出 `JOBWS_ALLOW_REUSE=1` 的出路 |
| 进程是否退出 | 是——`main.js` 走 `app.quit()` |
| **退出码** | **不可依赖**：`app.quit()` 不带码，实际是 `0`。**不要用退出码判断 Electron 这条路径**，只能看弹窗文案与进程是否退出 |

> 上一版文档说「退出码 2」对 Electron 也不成立——那是后端 `--host` 的码。

### 场景 2：显式复用（`JOBWS_ALLOW_REUSE=1`）

**在哪跑**：`web/backend/`

```powershell
# A 同上（数据根 X）
$env:JOBWS_ALLOW_REUSE = "1"
$env:JOBWS_DATA_DIR = "<根 Y>"     # 故意指向另一个根
python main.py --port 8765
```

**判据**：

| 观察点 | 期望 | 依据 |
|---|---|---|
| 退出码 | **0** | `main.py:287` |
| 实际服务的数据根 | **X（A 的），不是 Y** | `JOBWS_DATA_DIR` 只影响新进程，改不了已在跑的 |
| stdout | 「检测到服务已在运行，按 JOBWS_ALLOW_REUSE=1 复用并打开界面」 | `main.py:282` |

### 两项独立的证据，不能合成一条

| 证据 | 端点 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| **产品身份** | `GET /api/health` | `service == "jobws"`、`version` | 数据根（接口刻意不返回）、实例区分（手工启动时 `instance_id` 是空串） |
| **活动数据根** | `GET /api/system/paths?ws=personal` | `dataRoot` 是 X | 这个服务是谁拉起的 |

```powershell
# 证据 1：产品身份 + 版本
curl.exe -s http://127.0.0.1:8765/api/health

# 证据 2：活动数据根（这才是 X vs Y 的判据）
curl.exe -s "http://127.0.0.1:8765/api/system/paths?ws=personal"
```

**还要单独确认的两件事**（退出码正确证明不了它们）：

```powershell
# A 的 PID（用它判断"B 没有杀掉 A"）
Get-NetTCPConnection -LocalPort 8765 -State Listen | Select-Object OwningProcess

# A 的数据根文件在测量前后没有变化（用隔离目录，别用真实工作区）
# 比「相对路径 + 每个文件的 SHA256」，不要比字节总数——同样大小的文件可以被改写
Get-ChildItem "<根 X>" -Recurse -File |
  ForEach-Object { [pscustomobject]@{
      Path = $_.FullName.Substring("<根 X>".Length + 1)
      Hash = (Get-FileHash -LiteralPath $_.FullName -Algorithm SHA256).Hash } } |
  Sort-Object Path | Format-Table -AutoSize
# 前后两次输出逐行比对（或 Export-Csv 两份再 Compare-Object）
```

**为什么必须分开**：`exit 1` 只说明「B 没起来」，不说明「B 没碰 A 的数据」。
证明后者要回读 `dataRoot` + 比对文件。

### 为什么两个场景必须分开验

`JOBWS_ALLOW_REUSE=1` 时「用被复用的根」是 **ADR 的既定语义**（否则复用没意义）。
把「数据根不一致必须拒绝」当成统一判据，会与复用功能自相矛盾——
这个冲突在 `2026-10-28-p0-closure.md` §一 与 §八 之间出现过一次，已按模式拆开。
