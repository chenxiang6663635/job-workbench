## 发行工程结论

对照起点（10 月底仍无法交付一个只含两项依赖更新的安全补丁），本次采用的控制序列是正确的：

```
固定安全补丁源码 → 建立真实验证证据 → 接受有限残余风险
→ 分离 Tag / Draft / 公开授权 → 验证生产元数据与官网切换
```

值得保留的是这些**控制机制**，而不是把本次 D′-2 的全部探索性实现
升级为以后每个版本都必须通过的硬性流程。

三条建议固化为原则：

1. **Hotfix 优先交付已核实的安全修复** —— 测试工具的工程缺陷与产品缺陷必须区分。
2. **同一份证据只证明对应能力** —— 安装成功 ≠ 自动升级成功；元数据通 ≠ 用户完成重启；Actions 绿 ≠ 每个断言通过。
3. **发布后发现问题用 fix-forward** —— 26.10.1 资产应保持不可变；若需修复产品缺陷，评估新的 `26.10.2`，不替换同名 EXE。
