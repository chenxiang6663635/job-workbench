# 研究计划：求职工作台下一步功能差距分析（2026-09-03）

## 原始问题

还需要开发哪些功能？成熟项目有哪些好功能值得借鉴？

## 查询类型

**Breadth-first**。可拆成四个互不重叠的功能域，每个域独立检索，最后综合做差距分析。
与 2026-08-31 那份 `report_job_search_products.md` 的区别：那份是**产品化定位调研**
（架构、LLM 接入、差异化机会），本轮是**功能级清单差距分析**（我们具体还缺什么功能、
成熟度如何、值不值得做）。两份交叉印证，不重复劳动。

## 本项目现状基线（调研前的已知事实）

已交付：
- 4 个工作流（jd / apply / track / resume）+ 6 个 Python 脚本 + skills 分发到多 AI CLI
- Web 6 页面：看板（漏斗/方向/批次/待办/静默提醒/下钻）、追踪表（增删改+搜索排序+
  变更时间线+停留天数+阶段约束）、岗位池（JD 解析卡+四维评分下钻+硬门槛+证据标签）、
  简历工坊（标准版式数据驱动编辑+高级模板浏览生成）、素材库（事实库）、设置（BYOK Provider）
- 数据层：Markdown + CSV，tracker.csv 16 列 + history.csv 变更时间线
- 工程：workspace 抽象、file_lock 并发安全、Electron 桌面壳、PyInstaller onedir 打包
- 差异化：资格硬门槛前置（市面真空）、评分证据可追溯（精确/模糊/语义）

已知不做的雷区：自动投递 bot（AIHawk 被 LinkedIn C&D）、代登录、批量节流投递。

## 子任务与 subagent 分工（4 路并行，边界不重叠）

| # | 功能域 | 核心问题 | 必查对象 |
|---|---|---|---|
| 1 | **投递后全流程**：面试准备、联系人、薪资谈判、Offer 比较、提醒通知 | 投递之后到入职之间，成熟产品提供了哪些我们完全没有的能力？哪些对校招用户真有价值？ | Teal、Huntr、Simplify、JobCtrl、JobSync、Notion 求职模板生态 |
| 2 | **简历与 JD 匹配增强**：关键词覆盖、改写建议、封面信、ATS 解析模拟、多版本对比 | 简历侧除了生成 PDF，还有哪些高价值功能？JD↔简历差距分析怎么做？ | Resume-Matcher、Jobscan（闭源）、Reactive Resume、RenderCV、JSON Resume 生态 |
| 3 | **本地优先应用的基础工程能力**：备份恢复、导入导出、数据可移植、批量操作、版本快照 | 成熟的 local-first 应用在"用户数据安全与工程可靠性"上必做哪些？我们缺哪些？ | Obsidian、Logseq、Joplin、Standard Notes、Anytype、git 型工具 |
| 4 | **AI 增强与岗位发现**：BYOK 下高价值 AI 功能、岗位来源聚合/订阅 | 接入 LLM 后哪些功能是真需求而非噱头？岗位从哪来（不碰自动投递红线）？ | Resume-Matcher 的 LiteLLM 实践、Ollama 本地场景、岗位聚合源与 RSS |

每个 subagent 必须：
- 用 `web_search` + `web_fetch` 交叉核实，优先一手来源（官网、GitHub、官方文档）
- **尝试用 `use_skill` 加载 `wechat-article-search` 检索微信公众号（带 2025-2026 时间参数）**；
  若不可用或接口失败，明确说明"公众号源未能取回"并改用中文 web_search
- 输出：结论先行 + 对比表 + 明确标注"有据可查 vs 业界传闻" + References（可点击 URL）
- 范围边界：不讨论架构与商业化，只回答"有哪些功能、成熟度、用户价值"

## 各步预期产出

1. 四份子域功能清单（每条含：功能名、成熟度/谁在做、用户价值、实现成本量级）
2. 综合差距分析：对照本项目现状，标出【缺】【有但浅】【已有且更好】
3. 优先级建议：按"用户价值 × 实现成本 × 与本项目定位契合度"排序
4. 明确排除项（雷区与伪需求）

## 并行与必要性

四路完全独立，可并行。第 5 步（综合与辩驳）由主 agent 串行完成，不派 agent。
