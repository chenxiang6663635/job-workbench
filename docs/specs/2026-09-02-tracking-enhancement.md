# 追踪增强：看板下钻 + 状态时间线（2026-09-02）

## 背景与来源

用户提了两个问题：①看板上的数字能不能点进去看具体是哪些岗位；②追踪表的状态还缺什么。
结合 `docs/research/report_job_search_products.md` 的调研结论——追踪类开源产品的差异点
在**结构化数据模型**（JobCtrl 的双轴模型：终态不回退、状态跃迁带原因码、canonical 去重），
终态不回退与去重此前已落地，本轮补齐剩余缺口。

## 范围：6 项 P0（用户确认全做）

| # | 项 | 交付形态 |
|---|---|---|
| P0-1 | **看板下钻**：统计卡、漏斗柱、方向、批次可点击 | 点击后跳追踪表并预置对应筛选（hash 传参） |
| P0-2 | **状态变更时间线**：每次字段变更入账 | 新增 `05_投递追踪/history.csv`，追踪表行内展开查看 |
| P0-3 | **阶段停留时长**：在当前阶段停了多少天 | 追踪表列 + 看板停滞高亮，超阈值标红 |
| P0-4 | **静默提醒（已读不回）**：投递后长期无进展 | 看板独立卡片，默认阈值 14 天，非终态记录参与 |
| P0-5 | **关键字搜索 + 排序** | 追踪表搜索框（公司/岗位/备注）+ 排序（下次动作日期/评分/停留天数） |
| P0-6 | **下次动作日期可编辑 + 待办一键操作** | 追踪表内日期控件；看板待办项支持顺延 7 天 |

## 关键设计决策

### 时间线存哪里：独立 `history.csv`（三选一）

| 方案 | 取舍 |
|---|---|
| **独立 `history.csv`** ✅ | 记录数随变更线性增长，主表保持"一行一岗位"的当前状态快照；主表字段不变，旧文件与 Excel 打开方式不受影响；追加写，不重写全表 |
| 主 CSV 加列 | 主表会随时间无限膨胀，且 Excel 里同一岗位多行，违背"一行一岗位" |
| 每条记录一个 Markdown | 文件数随岗位数增长，无法跨记录做"最近变更"排序，统计停留天数要遍历全部文件 |

选独立 `history.csv`。字段：`时间, id, 字段, 原值, 新值`。
追加写入，新建时 `utf-8-sig`（Excel 中文不乱码），**追加时 `utf-8`**——否则每次追加都会在文件中间再写一个 BOM。

### 单一事实源

时间线的读写与 diff 计算全部落在 `tools/tracker.py`，Web 后端只做 HTTP 编排。
CLI 与 Web 走同一套函数，避免两处各写一份迟早不一致。

### 停留天数的基准日

按优先级回退：最后一次「当前阶段」变更日期 → `投递日期` → 最后一次任意变更日期 → 无（不参与判定）。

**投递日期优先于「任意变更」**：投递日期是用户声明的流程起点，而「任意变更」包含记录录入时间——
补录一条一个月前投的岗位时，若以录入时间为准就永远不会触发静默提醒，与语义相反。
「任意变更」只在既无阶段变更、又没填投递日期时兜底。

旧数据没有 history.csv 时自动退到投递日期，不需要迁移。

### 不做什么

- 不改主表 `tracker.csv` 的字段结构（16 列不变）
- 不做自动投递、不做邮件/日历集成
- 九级阶段不做收敛（调研建议留给后续"简化模式"，属独立议题）

## 验收

- CLI：`tracker.py add` / `update` 后在 `history.csv` 看到对应条目；`tracker.py history --id A001` 可查
- Web：看板任意统计单元可点击 → 追踪表带筛选；行可展开看时间线与停留天数
- 边界：终态记录不参与静默提醒；改非阶段字段也入账时间线；history 缺失时回退投递日期不报错
- 兼容性：Python 3.8 语法；CSV 一律 `utf-8-sig`（追加除外，见上）
