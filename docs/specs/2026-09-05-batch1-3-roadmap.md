# 第一批–第三批实施：设计与验收记录

日期：2026-09-05 起
前置：P0–P3 四批已全部落地（见 `2026-09-03-p0-p3-roadmap.md`）
来源：投递闭环后剩下的两类空白——**数据录入靠手敲**（简历、追踪表）、**产出只有 PDF**（网申系统要文本）

## 总原则

- **分三批、每批独立可验收**，一批做完跑完整验证交用户确认，随时可停
- 严守 6 个脚本上限：新能力一律落在既有脚本子命令或既有路由
- **不引入任何新运行时依赖**：PDF 用已有 `pypdf`，docx 用标准库 `zipfile` + XML，模型走既有 BYOK
- 诚实红线贯穿三批：简历导入是「**抽取**」不是「生成」，缺失留空、严禁补全

## 第一批 · 导入与导出闭环（已落地）

| 能力 | 落点 | 要点 |
|---|---|---|
| 简历一键导入 | `web/backend/resume_import.py` + `POST /api/resume/import` + `ResumeImportDialog.tsx` | PDF（pypdf）/docx（zip+XML）/md/txt 抽取文本 → BYOK 结构化 → **可溯源校验** → 核对页（未抽到标黄、疑似补全标红）→ 确认后才走既有 PUT 落盘 |
| 导入红线条款 | `resume_import.IMPORT_CLAUSE` + `tests/test_prompt_guardrails.py` | 与 `GUARDRAIL_CLAUSE` 同等地位，测试锁死（删句即失败）；条款四要点：只抽取 / 缺失留空 / 禁止补全推测 / 禁止美化数字 |
| 可溯源校验 | `resume_import.traceable_issues()` | 字段值归一化（去空白 + 全角转半角）后必须是原文子串，数字必须来自原文；不在原文中的列为「疑似模型补全，请核对」 |
| 追踪表 CSV 批量导入 | `tracker.py import` 子命令 + `parse_import_csv`/`preview_import`/`commit_import` + `POST /api/applications/import` | 两阶段：preview 只读出差异表，commit 才写入；提交持 `tracker.lock` 并重校验，冲突整批拒绝（返回 -1），绝不半批写入 |
| 导入预校验 | `tracker._validate_import_row()` | 必填（公司/岗位/方向/批次/阶段）、日期格式、阶段与批次与来源枚举、评分 0–100、终态必填原因、方向校验；产出 `ok`/`duplicate`（既有非终态或同批重复，可跳过）/`error` 三态并给出行号与原因 |
| 导出 Word | `GET /api/resume/{version}/doc` | 复用 `render_block` 渲染链路产出 HTML，补 Word 兼容头与 `meta charset`，`application/msword` 返回；**零依赖**，文件名走 RFC 5987 带中文名 |

### 关键取舍

- **导入端点绝不落盘**：只返回 `{text, data, issues, unfilled}`，写入必须经核对页逐段确认后走既有 PUT。没有「一键直接落盘」的捷径——这一页是诚实红线的物理载体
- **duplicate 不是 error**：同公司+岗位既有记录非终态 → 跳过（避免重复投递）；既有记录已终态 → 放行（挂了可以再投一次）
- **Word 版定位是「文本搬运」**：排版以 PDF 为准，按钮旁固定标注「Word 版只保证文本可复制」，绝不让用户误当正式交付物
- **隐私**：上传文件只落在系统临时目录，用完 `shutil.rmtree` 即删，不进工作区、不进快照、不进 git

## 第二批 · 面试与推进增强（已落地）

| 能力 | 落点 | 要点 |
|---|---|---|
| 面试题库 | `GET /api/progress/question-bank` + `QuestionBank.tsx`（进展页第四个子 Tab） | 按公司+岗位聚合 `interviews.csv` 的问题记录/我的回答要点/复盘，只收有「问题记录」的面试；关键词跨问题/回答/复盘/面试官匹配；组内按面试时间倒序、组间按问题数排序；纯只读，不做聚类（YAGNI） |
| 投递健康度 | `tracker.health_score()` + `SORTS` 增加 `health` + 行内徽章 | 四态：**urgent**（待投且距截止 ≤3 天，含已过截止）/ **overdue**（下次动作日期已过期）/ **stale**（停留超 `STALE_DAYS`）/ **ok**；终态返回 `None` 不参与判定；**reasons 收集所有命中理由，level 取最严重**（`HEALTH_LEVELS` 顺序），排序同级内停留久的在前 |
| 看板待推进 | `dashboard.py` 返回 `pending` + `PendingList` 卡片 | 与追踪表同源（都调 `tracker.health_score`，看板只做搬运，两处不会给出矛盾结论）；每条亮出完整理由，点击下钻到追踪表并预置健康度排序（`Drill.sort`） |

### 关键取舍（第二批）

- **reasons 全收、level 取最重**：一条记录既逾期又停滞时，只显示一个理由会误导用户以为只做一件事就够了
- **「已投」不看截止日紧急度**：截止日是投递闸门，投了就翻篇（否则已投岗位会永远挂红）
- **看板 pending 与追踪表 health 单一事实源**：都走 `tracker.health_score`，杜绝两处判据漂移

## 第三批 · 长期资产（已落地）

| 能力 | 落点 | 要点 |
|---|---|---|
| 失败原因聚类 | `report.cluster_failures()` + `retrospective()` 增加 `failureClusters` | 按工作区 `config/failure_keywords.txt`（每行「类别=词1,词2」，顺序敏感）聚合失败原因；文件缺失时退化为「状态原因」原文频次（`source=reason`），**绝不虚构分类名**；失败样本 < 3 条时 `shown=false` 并明确「样本太少，暂不展示」。关键词表随领域插件分发，改完刷新即生效 |
| JD 链接抓取 | `POST /api/jobs/fetch-jd` | urllib 抓取 + 去脚本/样式/标签取正文，按 Content-Type 或 meta charset 解码；写入 `01_岗位池/<公司>_<岗位>/JD原文.md` 并记录来源链接与抓取时间（原子写、持 `.jobs.lock`）。**失败与「正文过短（<80 字）」都明确降级**提示手动粘贴，绝不把半截内容当成功 |

### 关键取舍（第三批）

- **聚类口径交给用户**：分类关键词表放在工作区 config 下可自行维护，代码不写死——不同行业、不同方向的失败原因千差万别，写死等于替用户下结论
- **样本门槛**：三个样本以下谈「高频原因」是自欺欺人，宁可直说「样本太少，暂不展示」
- **抓取是尽力而为**：需登录、有反爬、纯 JS 渲染的页面抓不到是常态，所以失败路径要和成功路径一样被认真实现——降级提示里直接告诉用户下一步做什么（手动粘贴）

### 第三批踩坑记录

- `fails.append(a, b)` 这类「看似元组」的写法在 Python 里是传两个参数——聚类函数第一版就栽在这，冒烟脚本一跑即暴露（有冒烟脚本比只看代码可靠）
- 端到端抓取测试要避开真实外网：用 `http.server` 起本地页面（长正文 / 短页两个路径）既稳定又可覆盖降级分支

### 第二批踩坑记录

- 端到端「下钻未带排序」的假象：看板「近七天待办」与「待推进」可能出现**同名条目**（同一记录既临近截止又待办），测试脚本用全文匹配点到前者的行（写入的 drill 无 `sort`），误判为下钻失效。用作用域选择器定位「待推进」卡内的条目后复测通过——判定机制本身无缺陷。教训：**同名元素多处出现时，E2E 必须限定卡片作用域**。
