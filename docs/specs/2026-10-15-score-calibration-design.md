## 一、为什么做这个（问题陈述，不含解决方案）

用户（本项目维护者）在自用中提出一个**信念层面的怀疑**，原话是「为什么他们要看评分才投? 为什么不海投? 这个项目的初衷就好像错了」，追问他指出真实触发点是「**看到别人海投拿到机会、反过来怀疑自己这套太窄**」。

关键澄清（brainstorming 产出）：**痛不在工具，在信念**——不是「这个功能不好用」，而是「我这套先评分再投，可能在让我漏机会」。所以这不是一个功能缺失问题，而是一个**校准问题**：他现在的筛法是**先验**（评分决定投不投），而工具里已经躺着**后验**数据（每一投的结局）。两者从未被接起来过。

**因此本特性要回答的问题只有一句**：*我按评分筛的这一套，测出来的结果支持它吗？*

它**不**回答「该不该海投」，也不**替**用户决定放宽阈值——见 §四 反目标。

## 二、三个输出（本批交付的完整定义）

### 输出 ① 按评分档位的转化率

**做法**：先由 tracker 的「评分」列取档位，再与所有**已投递**记录的结局 join，逐档给出转化链路。

- **档位来源**：复用 `packages/jobws-core/src/jobws_core/jd_score.py` 的 `THRESHOLDS` 与 `verdict()`（现有唯一档位实现；**不新造分档口径**）。tracker 的「评分」列是 0–100（`tracker/_schema.py:19-23`），**空 = 未评分**（没有 `-1` 哨兵）；未评分岗位**不参与**分档统计（「还没评」不等于最低档——沿用 `web/backend/routers/dashboard.py:66` 的既有口径）。
- **分母（**本设计的核心口径，请重点确认**）**：**分母 = 该档位里「投过」的岗位数**，不是该档位里的全部岗位数。
  理由：本输出要回答的是「**投出去之后**成不成」，把没投的算进分母，等于把「我筛掉了它」这件事混进「它转化好不好」，两个问题会被搅成一个。没投的那部分由**输出 ②** 单独回答。
- **分子/链路**：按 `report.py` 的既有阶段枚举 `FUNNEL_ORDER`（`STAGES + TERMINAL_STAGES`，`:28`）取「简历通过 / 面试 / offer」这些节点。**首个实现必须复用 `report` 里既有的阶段语义与 `conversion` 口径**（`report.py:243-257`），不允许在看板侧另写一套「什么叫通过」。
- **样本下限**：逐档给出 `shown` 标志 + `noteCode`，**照抄** `report.cluster_failures` 的成熟范式（`MIN_CLUSTER_SAMPLES = 3`，`report.py:125`）：样本不足时 `shown=false`、`noteCode="too_few_samples"`、`noteParams={total, min}`，**不硬凑数字**。理由与失败聚类同源——**样本太少时给一个百分比比不给更害人**（会让人按噪声调策略）。

### 输出 ② 未投递岗位的记账（只读）

**做法**：枚举岗位池里**没有**对应 tracker 行的岗位，给出数量与构成。

- **可枚举性**（已核）：以 `apply_state == "未投递"` 为口径，实现见 `web/backend/routers/progress/job_dirs.py:121-128`。
- **构成**：至少区分「硬门槛合格但没投」「硬门槛不合格」「未评分」三类——这正是「窄」的代价所在（硬门槛合格 + 评分中等 + 被放掉的那一批，是「可能漏掉的机会」的唯一可见面）。
- **本批只读**：只统计与呈现，**不新增写入口**。原因见下条。

### 输出 ③ 节点复盘的人话结论

在 ① ② 之上给**一句**结论，例如「数据显示：你的 80 分档与 60 分档的简历通过率没有可见差异（样本 N=…），筛法可能偏紧」——**措辞一律是「数据显示 + 可能」，不是「你该放宽」**。

## 四、反目标（危险形态，必须成文）

本特性的失败形态不是「算错」，而是**长成它不该成为的东西**：

1. **不许自动放宽阈值**。仓库红线（`keep-writes-human-confirmed.md:20`）禁的是自动投递 / 代登录 / 替用户选 offer，**没有**明文禁「自动放宽阈值」——正因为如此，这里必须自己声明：**本特性不改任何阈值、不写任何配置、不生成投递动作**。
2. **不许把「建议纳入哪一档」写成祈使句**。输出一律是**事实呈现 + 用户决策**：给数字、给样本量、给不确定性，结论句带「可能 / 数据显示」。**替用户下判断就是越界**。
3. **不许拿小样本当趋势**。样本不足必须 `shown=false`（输出 ① 的下限），且**不得**用「把相邻档合并」的方式凑出好看的样本量——合并档位是另一件事，要做也得单独立项并显式声明。
4. **不许做成「多投一点」的推手**。本特性只把**已经发生的事**摊开（投了的结果、没投的规模）；它的价值在于**让信念可被数据检验**，不在于提高投递量。

## 五、匹配键与已知取舍（必须写进输出）

- **岗位池 ↔ tracker 的匹配键 = 目录名**（公司名与岗位名由首个下划线切分，`job_dirs.py:47-54`）。**公司名自带下划线时会误判「未投递」**——输出（②）必须带这条已知取舍的说明，不能装作精确。
- **两套评分互不校验**：tracker 的「评分」列与解析卡的总分是**各自独立填写**的，本特性按 tracker 列为准（因为要 join 的是投递记录），输出里要说明这一点。
- **「放掉」无落点**：② 只能给出「没投」的**规模与构成**，**给不出「当时为什么放」**——因为那个动作没有留下任何数据。若要让「放掉」可解释，需要**新增写入口**（必然两段式 + 进 history 时间线 + 改 schema 面），**本批不做，单独立项评估**。

## 七、性能纪律

沿既有「**一份原文读一次**」纪律（`tests/test_read_amplification.py` 守着）：档位聚合只读 tracker 一次、岗位池只扫一次目录（复用 `job_dirs` 的既有解析），不得为每个岗位重读解析卡。聚合复杂度 O(n log n)（排序）以内，无热点。

## 八、验收判据（实现批必须逐条给证据）

1. **分母口径**：构造「同档位 1 投 + 2 未投」的数据，断言分母是 1（不是 3）；
2. **未评分不入档**：未评分岗位不出现在 ① 的任何档里，但出现在 ② 的构成里；
3. **样本下限**：某档投递数 < `MIN_CLUSTER_SAMPLES` 时 `shown=false` + `noteCode="too_few_samples"`，且**不输出百分比**；
4. **反目标**：断言调用本特性**不产生任何写请求**（不写配置、不写 tracker、不调 `preview_*`）——用请求监听或写口 mock 钉死；
5. **四端同源**：CLI / MCP / API 三处对同一份数据给出**逐字段相同**的档位与转化数字（同一实现，不是三套）；
6. **匹配键说明**：输出携带「首个下划线切分」的已知取舍说明（公司名带下划线的用例要能复现误判并按说明呈现，而不是静默给错数）。

## 九、请确认的三点（确认后才进实现）

1. **分母 = 该档位里「投过」的岗位数**（§二 输出 ①）——这是本设计的关键口径，也是最容易做错的一处；
2. **档位沿用现有 `THRESHOLDS` 五档**，逐档给、样本不足即 `shown=false`（**不合并相邻档**凑样本）；
3. **「放掉记账」的写入口本批不做**，只做只读的 ②（规模与构成），写入口单独立项评估（因为它要动 schema 面与两段式写入）。
